Specline — the project spine

Usage: specline [OPTIONS] <COMMAND>

Commands:
  fsck              Check the store's referential integrity
  doctor            Ask whether anything has quietly gone wrong
  ui                Open the interface in a browser
  hook              Run a Claude Code session hook. Called by the plugin, not by a person
  reembed           Give every current revision that has no vector one
  backup            Back up the store: one consistent snapshot, plus a manifest
  restore           Restore a backup into an empty directory
  migrate           Apply any schema migrations the store is missing
  fixture           Load the realistic fixture corpus into an empty store
  import            Import markdown files into Specline as versioned documents
  bootstrap         Seed Specline's own project — the dogfooding switch
  release-manifest  Print what a release of this binary promises, as JSON
  update            Install the latest release, if it cannot change the store's shape
  status            Print a one-line summary of what is in the store
  generate          Regenerate a project's repository files from Specline
  gate              Score Phase 2's exit criterion from the event log
  render-status     Print the generated tracker for a project to standard output
  note              Append to a row's running commentary, or read it back
  archive           Archive a row. Soft delete — it stays on disk and stops appearing
  lint              Report the rows a reader would struggle with. Never rewrites one
  next              What can be worked on right now, best first
  claim             Take a task: move it to in_progress and record who is on it
  close             Close a task, saying why and showing the work
  task              Create a task row
  signal            File a signal into the Inbox — something somebody wants, before anybody has decided whether to build it
  triage            Triage a signal: pick it up, or set it down with the argument
  help              Print this message or the help of the given subcommand(s)

Options:
      --home <HOME>
          Where the store lives. Defaults to `~/.specline`.
          
          `specline-core` never reads the environment; resolving this is the CLI's job, which is why the flag exists here and not there.
          
          [env: SPECLINE_HOME=]

      --json
          Print machine-readable JSON instead of prose

      --force
          Write to the store even though a daemon appears to be running.
          
          Every command that writes probes for a daemon first and refuses if one answers, because the daemon owns the single write path and a write that goes round it skips six of the seven steps. This is the escape for the cases where a person knows better — a wedged daemon, a store being repaired. A flag rather than an environment variable, so that using it shows up in a shell history.

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version

===== doctor =====

Composes every read-only check there is — the file's own integrity, referential integrity, whether search has any vectors, whether the committed markdown still matches the store, how old the backup is, and whether the clock has stepped — into one page.

Exits non-zero only for a real problem. A degraded store says so without failing, because a check that cannot tell the two apart is one nobody can put in a hook.

===== hook =====

Run a Claude Code session hook. Called by the plugin, not by a person.

These were shell scripts until KEEL-206, and they needed `python3` and `curl` — neither declared anywhere, and `python3` absent on a Mac until the Xcode command line tools arrive. Every failure path exited 0 silently, so on a fresh machine they did nothing and it looked exactly like Specline not working.

Both read a JSON payload on stdin and write JSON on stdout. Both exit 0 whatever happens: a hook that can block a session is worse than a hook that misses a record.

===== lint =====

Report the rows a reader would struggle with. Never rewrites one.

Three rules arrived after most of this store existed — a task needs a summary, a close needs a reason, prose should not lean on a bare identifier — and none of them can be enforced backwards. This is the list a person works through.

It does not fix anything, and that is the design: a machine filling in a missing summary would write exactly the confident, plausible, wrong prose the requirement exists to prevent.

===== migrate =====

Apply any schema migrations the store is missing.

Nothing else applies them to a store that already exists. A migration changes what every process believes the tables look like, so it happens when someone asks for it and the daemon is stopped — not as a side effect of whichever command opened the store first after an upgrade.

Usage: specline migrate [OPTIONS]

Options:
      --daemon <DAEMON>
          The daemon to check for before touching anything.
          
          Same default and same environment variable as every other command with this flag. A migrate pointed at a port nothing is listening on would conclude no daemon is running and change the schema under one that is — which is the exact failure this command exists to prevent, arriving through a typo in its own default.
          
          [env: SPECLINE_DAEMON_URL=]
          [default: http://127.0.0.1:7654]

      --home <HOME>

===== next =====

Open work with nothing live in its way, grouped and then oldest first. What a task unblocks still leads where that means something; on a store where nothing blocks anything it does not, so the group decides (B-83).

The same computation the MCP tool and the app read. There is one ranking, so the three cannot disagree.

`ready` still works. It was the name until B-85, and a verb somebody has in a shell history should not start erroring over a rename.

===== reembed =====

Give every current revision that has no vector one.

Embedding happens on the way into a new revision and nowhere else, so turning the feature on leaves the existing corpus invisible to the vector half of hybrid search — permanently, because nothing would ever rewrite those rows. This is the pass that fixes that.

The first run downloads the model, which needs network access.

===== release-manifest =====

Print what a release of this binary promises, as JSON.

The updater has to decide whether a new version is safe to apply *before* it downloads it, and it cannot ask the candidate binary — running the thing you are deciding whether to run is the whole problem. So each release publishes this alongside its artifacts and the updater reads it first.

Opens no store, which is the point: it is run in a release job against a freshly built binary on a machine that has no Specline home at all.

Usage: specline release-manifest [OPTIONS]

Options:
      --home <HOME>
          Where the store lives. Defaults to `~/.specline`.
          
          `specline-core` never reads the environment; resolving this is the CLI's job, which is why the flag exists here and not there.
          
          [env: SPECLINE_HOME=]

      --json
          Print machine-readable JSON instead of prose

      --force
          Write to the store even though a daemon appears to be running.
          
          Every command that writes probes for a daemon first and refuses if one answers, because the daemon owns the single write path and a write that goes round it skips six of the seven steps. This is the escape for the cases where a person knows better — a wedged daemon, a store being repaired. A flag rather than an environment variable, so that using it shows up in a shell history.

  -h, --help
          Print help (see a summary with '-h')

===== signal =====

File a signal into the Inbox — something somebody wants, before anybody has decided whether to build it.

A signal is not a task. Nothing has been committed to, there is nothing to claim, and it stays out of `next` and out of the open count until somebody triages it. The only required argument is what was said, because capture that costs more than the thought did is capture that does not happen.

Usage: specline signal [OPTIONS] --project <PROJECT> <SUMMARY>

Arguments:
  <SUMMARY>
          What was said, in their words. Not a title — a signal has none

Options:
      --home <HOME>
          Where the store lives. Defaults to `~/.specline`.
          
          `specline-core` never reads the environment; resolving this is the CLI's job, which is why the flag exists here and not there.
          
          [env: SPECLINE_HOME=]

      --project <PROJECT>
          Project id, slug or name

      --json
          Print machine-readable JSON instead of prose

      --kind <KIND>
          interview, support, sales, idea, competitor, observation
          
          [default: idea]

      --force
          Write to the store even though a daemon appears to be running.
          
          Every command that writes probes for a daemon first and refuses if one answers, because the daemon owns the single write path and a write that goes round it skips six of the seven steps. This is the escape for the cases where a person knows better — a wedged daemon, a store being repaired. A flag rather than an environment variable, so that using it shows up in a shell history.

      --source <SOURCE>
          Who said it, or where it came from

      --contact <CONTACT>
          How to reach them, if closing the loop will need it

      --occurred-at <OCCURRED_AT>
          When it was said, if that was not today

      --body <BODY>
          The verbatim, or the context. Optional, and kept when given

  -h, --help
          Print help (see a summary with '-h')

===== triage =====

Triage a signal: pick it up, or set it down with the argument.

A signal cannot leave the Inbox without an outcome, which is why this is a verb of its own rather than a field somebody sets. Setting one down is not deleting it: the argument is written onto the signal where search will find it, and the same idea arriving in four months finds the reasoning instead of silence.

Usage: specline triage [OPTIONS] <ID>

Arguments:
  <ID>
          The signal, `fbk_…`

      --feature <FEATURE>
          Pick it up: the `spc_…` feature spec making the case for building it

This is the escape for the cases where a person knows better — a wedged daemon, a store being repaired. A flag rather than an environment variable, so that using it shows up in a shell history.

===== ui =====

Open the interface in a browser.

The daemon serves the read surface itself, compiled in, so this needs no Node and no second process — it works out where the daemon is listening and opens that. Which matters more than it sounds: the daemon records the address it actually bound, so a daemon told to use another port is still found without anyone remembering the number.

It refuses rather than opening a browser at a dead port. A tab showing "cannot connect" is a worse answer than a sentence saying the daemon is not running.

Usage: specline ui [OPTIONS]

Options:
      --daemon <DAEMON>
          Daemon base URL. Defaults to `$SPECLINE_DAEMON_URL`, then the address the running daemon recorded, then the local default
          
          [env: SPECLINE_DAEMON_URL=]

      --home <HOME>
          Where the store lives. Defaults to `~/.specline`.
          
          `specline-core` never reads the environment; resolving this is the CLI's job, which is why the flag exists here and not there.
          
          [env: SPECLINE_HOME=]

      --json
          Print machine-readable JSON instead of prose

      --print
          Print the address instead of opening anything.
          
          For a machine with no browser, and for anyone who would rather paste it themselves.

      --force
          Write to the store even though a daemon appears to be running.
          
          Every command that writes probes for a daemon first and refuses if one answers, because the daemon owns the single write path and a write that goes round it skips six of the seven steps. This is the escape for the cases where a person knows better — a wedged daemon, a store being repaired. A flag rather than an environment variable, so that using it shows up in a shell history.

===== update =====

Install the latest release, if it cannot change the store's shape.

A release that agrees with this one about the schema is interchangeable as far as your store is concerned, so it is applied without asking. One that moves the schema stops here and waits for you, because a migration rewrites data and `--rollback` puts binaries back, not rows.

Downloaded from the latest release over plain HTTPS — no account and no token — and checked against the SHA-256 in the release manifest before anything is moved into place.

Usage: specline update [OPTIONS]

Options:
      --check
          Say what would happen and change nothing

      --home <HOME>
          Where the store lives. Defaults to `~/.specline`.
          
          `specline-core` never reads the environment; resolving this is the CLI's job, which is why the flag exists here and not there.
          
          [env: SPECLINE_HOME=]

      --json
          Print machine-readable JSON instead of prose

      --rollback
          Put back the binaries the last update replaced.
          
          One generation only, and binaries only. If the update you are undoing migrated the store, this does not undo that — restore a backup.

      --daemon <DAEMON>
          Daemon base URL. Defaults to `$SPECLINE_DAEMON_URL`, then the local daemon.
          
          Replacing the binaries is half of an update: the daemon is another process and goes on running what it loaded at startup. This is the one asked to restart into the new version afterwards, and the one checked to see which version came back.
          
          [env: SPECLINE_DAEMON_URL=]
          [default: http://127.0.0.1:7654]

      --force
          Write to the store even though a daemon appears to be running.
          
          Every command that writes probes for a daemon first and refuses if one answers, because the daemon owns the single write path and a write that goes round it skips six of the seven steps. This is the escape for the cases where a person knows better — a wedged daemon, a store being repaired. A flag rather than an environment variable, so that using it shows up in a shell history.

  -h, --help
          Print help (see a summary with '-h')
