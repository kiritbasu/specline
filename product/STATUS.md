- **KEEL-349** Put semantic search in a released binary, by loading the ONNX runtime instead of linking it `p2` · release, build, search

  Comes out of KB asking for embeddings to work in production with no manual setup (B-95). Everything else that asks for is done; this is the half that decides whether "anyone downloading the app" means anyone at all.
  
  **Where it stands.** `[package.metadata.dist] default-features = false`, so every released binary is built without `specline-embed`. That was route 1 of KEEL-252 and it was the right call then: `dist build` takes `--target` and not `--features`, and two of three targets could not link ONNX. Re-checked on 2026-08-19 against `ort-sys` 2.0.0-rc.13 — its `build/download/dist.tsv` lists nine prebuilt targets and `x86_64-apple-darwin` is still not among them. `x86_64-unknown-linux-gnu` *is* there now, against ONNX Runtime 1.28.0, so the Linux half of the original blocker may already have expired.
  
  **The route that gets all three.** `fastembed` exposes `ort-load-dynamic`, which forwards to `ort/load-dynamic` and thence to `ort-sys/disable-linking`. With it, nothing about ONNX is decided at build time: the crate dlopens the library from `ORT_DYLIB_PATH` when the first model loads. Every target compiles, including the one that has no prebuilt at all, because there is nothing to link.
  
  The library then has to come from somewhere, and there are two shapes:
  
  - **In the archive.** Ship `libonnxruntime` beside the binary for each target and have the daemon point `ORT_DYLIB_PATH` at a path relative to its own executable. Predictable, offline, and it makes the download bigger.
  - **On first use.** Fetch it the way the model is fetched. Smaller archive, one more thing that can fail on a train, and on macOS a dylib we downloaded ourselves carries a quarantine attribute — whether `dlopen` will touch it is the first thing to test, not the last.
  
  **What to verify before committing to either**, in this order, because the cheapest one can kill the idea: that `ort` 2.0.0-rc.13 loads a Microsoft-published 1.28.0 dylib at all; that a quarantined dylib opens on macOS; that an Intel macOS build actually runs the model rather than merely linking; and only then the release plumbing.
  
  **Not to be done quietly.** It changes what a release *is* — three archives that are currently uniform in capability, and this makes them uniform in a different way. KEEL-252 recorded that a release config cannot be proved by "it did not complain", and that applies twice over here.

- **KEEL-278** Import matches a file to an artifact by its heading, so a drifted title makes a duplicate `p2` · cli, storage, data-safety

  Hit twice while renaming, and the second time it made a duplicate.
  
  `import` decides which artifact a file belongs to by its **H1 heading**, not by its `mirror_path`. For most documents the heading and the stored title agree, so the match works and the file revises the artifact it came from. When they disagree, import has no idea the artifact already exists and creates a second one — with the same `mirror_path` as the first.
  
  `product/DEPENDENCIES.md` is the worked example. Stored title:
  
  ```
  Dependency and protocol verification — 2026-08-09 snapshot
  ```
  
  The body's own H1:
  
  ```
  # Dependency and protocol verification — a snapshot, not a description
  ```
  
  Importing the file created `spc_01M05K5F37VVBDQDPGTD04XZNH` beside the existing `spc_01KZPJXC5RG006KJANQ6G4TBQS`, both claiming `product/DEPENDENCIES.md`. The duplicate was archived and the edit written to the original with `specline_write_doc`, which takes an id and therefore cannot make this mistake.
  
  **Two documents claiming one path is the failure `generate` is built to prevent** — it goes to some trouble to stop an adopted document also being written into the mirror, for exactly this reason. Import can create the condition from the other side, and nothing notices: generation would have written whichever it reached last.
  
  Worth considering, roughly in order of how much they cost:
  
  - **Match on `mirror_path` first, heading second.** A file at a path an artifact already claims is that artifact, whatever its heading says. This is the cheap fix and probably the right one.
  - **Refuse rather than create** when the resolved path is already claimed, and say which artifact has it. Loud, and leaves the person to decide.
  - **`fsck` should report two live artifacts sharing a `mirror_path`.** It already reports a duplicated readable id for the same reason; this is the same class and currently invisible.
  
  Also worth knowing: the stored title and the body's H1 drifting apart is legal and undetected, which is what made this possible. That may deserve a lint of its own.

- **KEEL-261** Two update checks can stage at once, and the marker can end up describing binaries it did not come with `p2` · updates, daemon

  Found reviewing this session's own work.
  
  `POST /api/update/check` (KEEL-258) runs the same `check_and_stage` the hourly task runs, on a separate tokio task, with nothing between them. `specline-update`'s `stage` does:
  
  ```rust
  let partial = into.join(format!("{name}.staged.partial"));
  // copy, chmod, rename to <name>.staged
  …
  // last, and only once both binaries are whole
  std::fs::write(into.join(STAGED_VERSION), version)
  ```
  
  The partial path is fixed rather than unique, so two concurrent stages write the same file. The comment above the marker write states the invariant the design rests on — *"last, and only once both binaries are whole"* — and that invariant is a property of one writer, not of the code.
  
  **The probability is low and the failure is the bad kind.** Both checks normally fetch the same manifest and write identical bytes, so an interleave is invisible. It needs a release published between two overlapping checks: the hourly timer firing while somebody clicks, or two clicks across two open interfaces. What it produces is `specline` from one version, `specline-daemon` from another, and a marker naming whichever finished last — then `apply_staged` promotes the pair, and the two binaries disagree about the shape of a store they share. Nothing errors.
  
  This is the class the advisory lock exists for (B-60), arriving through a door that lock does not cover.
  
  **Remedy:** a `tokio::sync::Mutex` on `AppState`, `try_lock` in the handler, 409 with "a check is already running" when it is held. The background task takes the same lock. About ten lines, and it makes the invariant true rather than customary.
  
  Worth considering while there: `stage` could write to a unique partial path per run, which removes the shared-file half of the race independently of who is calling.

  Before trusting any of it, diff the fixture's table-shape coverage against the real store's and treat every gap as a case the fixture cannot speak for. Scrubbing needs deciding too — what has to come out before a store can sit in a public repository.
  
  The test asserts row counts per table and content hashes per document, and runs `fsck` afterwards. Assert equality; do not eyeball it.

- **KEEL-187** Drop documents.embedding, and take the dead trigger clause with it `p2` · storage, cleanup

  B-55 moved vectors to `document_chunks` and said `documents.embedding` stays "until a later migration takes it". This is that migration, and there is a second thing to do in the same one.
  
  **The column.** Nothing writes it — the only remaining assignment is in a test fixture — and nothing reads it. `search_semantic` reads passages. It is dead weight in every row of the largest table.
  
  **The trigger clause.** `prose_archive_triggers` still ends with:
  
  ```sql
  UPDATE documents SET embedding = NULL, embedding_model = NULL
    WHERE entity_id = new.id;
  ```
  
  That runs on every archive and blanks a column that is already blank. Harmless today, and it is the reason to do these together: a trigger referring to a dropped column fails when it *runs*, not when anything compiles. The symptom would be archiving suddenly erroring, some time after the migration that caused it, with nothing connecting the two. Triggers are the worst place to leave dead code because nobody reads them.
  
  Flagged as a required fix in review and then reconsidered, honestly: on its own it needs a migration to drop and recreate five triggers, which is the same migration this task needs anyway. Two migrations for one cleanup is worse than one, and the clause cannot bite until the column goes.
  
  Worth being careful about:
  
  - SQLite cannot drop a column that an index or trigger references, and older versions cannot `DROP COLUMN` at all. Check what the bundled amalgamation supports before assuming; the fallback is the twelve-step table rebuild, which is a different size of job.
  - The recreated triggers must keep the two things that are *not* dead — removing the row from `fts_source`, and deleting its passages. Losing either resurrects KEEL-175.
  - `a_restored_document_keeps_its_embedding` and anything else asserting on that column will need to move or go.
  - Verify on a copy of the live store, and check archiving still works afterwards rather than only that the migration applied.

- **KEEL-184** Generated files and stored bodies differ by a trailing newline, so re-importing one is not a no-op `p2` · cli, storage

  Found by `specline import --dry-run` the first time it was pointed at real files, which is a decent argument for the flag.
  
  ```
  revise     product/SPEC.md  →  Specline — Technical Specification
  unchanged  product/PRD.md   →  Specline — Product Requirements Document
  unchanged  product/JOURNAL.md → Specline — Build journal
  ```
  
  `specline generate specline --check` says SPEC.md is current, so the store-to-file direction is fine. The difference is one byte in the other direction:
  
  ```
  store bytes : 68690    tail: 'rDB/falkordb-rs-next-gen)'
  disk  bytes : 68691    tail: 'DB/falkordb-rs-next-gen)\n'
  ```
  
  The stored body has no trailing newline and the generated file does. `body_hash` covers title and body, so that one byte is a different hash and the import would write a revision that changes nothing anyone can read.
  
  It is per-document rather than systemic: PRD and JOURNAL round-trip clean, so their stored bodies already end with a newline. SPEC's does not, presumably from however it was first written.
  
  This contradicts what `import`'s own module doc promises — "re-importing an unchanged file does nothing at all — so it is safe to re-run during the migration". For a generated file that is not reliably true, and the failure is invisible: an extra revision looks like an edit somebody made.
  
  Two ways to fix it and they are not equivalent. Normalising on the way *in* — ensuring a stored body ends with exactly one newline — fixes it for every document and quietly rewrites one existing body. Writing the body verbatim on the way *out* leaves the file without a trailing newline, which most tools and every `diff` will complain about. The first is probably right, but it changes stored content, so it wants deciding rather than assuming.
  
  Worth checking whether the same gap exists in `specline_write_doc` over MCP, since that is the path that writes most bodies now.

  - The scope is bigger than the one document that surfaced it. **105 of the live current documents have a body with no trailing newline**, so the round trip is one-byte-lossy for most of the store, not for SPEC alone.  SPEC.md itself is now clean, incidentally rather than deliberately: annotating §13 for TQ-37 meant importing the file, and the imported body carried the trailing newline the generated file has. Re-importing it now reports `unchanged`. That is one document out of 105 and it does not close this.  It also sharpens which fix is right. Normalising on the way in would rewrite 105 stored bodies — a revision each, all of them differing by one invisible byte, which is a lot of history for nothing anyone can read. Worth considering a third option the task did not list: normalise on *comparison* rather than on storage, so `body_hash` is computed over a body with trailing whitespace trimmed. That makes the round trip a no-op without rewriting anything, at the cost of two documents differing only in trailing whitespace being treated as the same document — which, for markdown, they are.  Still worth checking `keel_write_doc`: if it stores exactly what a model sends, and models rarely end a body with a newline, that is where the 105 came from. <sub>— claude · 2026-08-13</sub>

- **KEEL-96** Pruning does not cover adopted files under product/ `p3`

  `specline generate` prunes orphaned files under `.keel/` using the previous manifest (KEEL-96 / TQ-28), but adopted prose files in `product/` are not covered.
  
  An adopted file orphans when its artifact is archived — `product/QUESTIONS.md` and `product/DECISIONS.md` both did on 2026-08-10 and were removed by hand with `git rm`.
  
  Why it was left: deleting inside `product/` is a larger act than deleting inside `.keel/`. A mirror file is Specline's own bookkeeping; an adopted file is a document someone may have 50 KB of prose in. The manifest does not currently record adopted paths, so the safe set is not even known.
  
  What it needs: record adopted paths in the manifest, then prune them on the same rule. Worth pairing with a louder confirmation than mirror pruning gets — or reporting rather than deleting, which is the asymmetry TQ-28 already accepts for `--check`.
